# Northlake Savings

An interactive savings-growth dashboard built for a mathematics project on
**compound interest**. It presents a fictional high-yield savings account with
roughly six and a half years of deposit history, monthly interest postings, a
connected external account, and a projection tool for exploring how the inputs
change the outcome.

**Northlake Savings is not a real financial institution.** Every figure on
every screen is generated by the model in `lib/simulation.ts`. Nothing here is
a record of anything that happened.

## Quick start

```bash
npm install
npm run dev          # http://localhost:3000
```

Sign in with **`demo` / `northlake`** — both fields are prefilled, so the
sign-in button is enough. (The credentials are no longer printed on the page;
change them in `lib/config.ts` under `DEMO_CREDENTIALS`.)

| Command | What it does |
|---|---|
| `npm run dev` | Development server |
| `npm run build` | Production build |
| `npm start` | Serve the production build |
| `npm run export` | Fully static site in `./out` |
| `npm run verify` | Re-run the model and assert the arithmetic |

## Deploying

### Vercel (easiest)

1. Push this folder to a GitHub repository.
2. Go to [vercel.com/new](https://vercel.com/new), import the repository.
3. Accept every default and deploy. Vercel detects Next.js on its own — there
   is nothing to configure and no environment variable to set.

To use your own domain: **Project → Settings → Domains → Add**, then point the
domain's DNS at Vercel with the record it displays.

### Any other host (cPanel, Hostinger, Netlify, GitHub Pages, S3)

```bash
npm run export
```

This writes a complete static site to `./out` — plain HTML, CSS and JavaScript
with no server component. Upload the **contents** of `out/` to your web root
(`public_html`, or wherever the host serves from). It will run on any static
hosting, including free tiers.

## The model

The account is not a stored list of transactions. It is **replayed from
scratch** every time the app loads, one statement cycle at a time, from the
settings in `lib/config.ts`.

Each month the model:

1. Takes the recurring transfer from the connected external account.
2. Adds any one-off top-up scheduled for that month.
3. Posts interest on the closing balance:

```
   interest = balance × (APR ÷ 12)
   balance  = balance + deposits + interest
```

Because each month's interest joins the balance, the next month's interest is
calculated on a larger figure. That is compounding, and it is why roughly
**11% of the current balance was never deposited by anyone**.

The effective annual yield shown in the UI is derived from the nominal rate:

```
   APY = (1 + APR ÷ 12)¹² − 1
```

Interest posts only once a statement cycle has closed, so the current month
shows its deposit but not yet its interest — the same way a real cycle behaves.

### Money is held in integer cents

Currency in floating point accumulates error across ~90 compounding steps, and
the accuracy of that accumulation is the whole subject here. All internal
arithmetic uses integer cents, so the books reconcile exactly:

```
opening deposit + Σ deposits + Σ interest === closing balance
```

`npm run verify` asserts exactly that, along with the running balance on every
ledger line. Run it after changing anything in `lib/config.ts`.

## Changing the numbers

Everything tunable lives in **`lib/config.ts`** — there are no magic numbers
anywhere else in the codebase.

| To change | Edit |
|---|---|
| Bank name, tagline | `BRAND` |
| Account holder, masked number | `ACCOUNT_HOLDER` |
| Connected external account | `LINKED_ACCOUNT` |
| Where the history starts | `START_YEAR` / `START_MONTH` |
| The closing balance | `OPENING_DEPOSIT`, `MONTHLY_CONTRIBUTION` |
| One-off deposits | `LUMP_SUMS` |
| Interest rates per year | `APR_BY_YEAR` |
| Demo login | `DEMO_CREDENTIALS` |

After any edit:

```bash
npm run verify
```

It prints the resulting balance, the year-by-year breakdown, and fails loudly
if the arithmetic stops reconciling.

**Note on the balance.** It is *derived*, not typed in — currently
**$69,549.16**. Raising `MONTHLY_CONTRIBUTION` by about $10/month moves the
closing balance by roughly $1,000. The figure also grows slowly on its own,
because the model runs to the real current date. To freeze it, set
`AS_OF = "2026-07-31"` (or any date) in `lib/config.ts`.

**Note on the timeline.** The brief asked both for deposits "dating back to
2019" and for "approximately six years" of history; those no longer describe
the same span. The model follows the 2019 start date and the UI reports the
true elapsed time. For exactly six years, set `START_YEAR` to six years before
the current date.

## Adding a database later

The app currently needs no backend — the model is deterministic, so every
device computes identical figures with no network call. When you want real
persistence, **[Supabase](https://supabase.com)** is the easiest drop-in: free
tier, hosted Postgres, works from any device, no server to run.

The seam is already in place. `getSimulation()` in `lib/simulation.ts` returns
plain serialisable objects, so:

1. Create a Supabase project and a `transactions` table matching the
   `Transaction` interface in `lib/simulation.ts`.
2. Seed it once by running the model and inserting the output.
3. Replace the `getSimulation()` call in the three page components with a
   Supabase query. Nothing else changes — the charts and tables only ever see
   that shape.
4. For real sign-in, swap `lib/session.ts` for Supabase Auth. The current
   version is a demo gate, not security: the credentials are printed on the
   sign-in page and all model data ships in the JavaScript bundle.

## Design notes

**Charts are hand-drawn SVG.** No charting library, which keeps the bundle
small and makes the mark specifications exact rather than approximated: 2px
gaps in the surface colour separate stacked bands, bars are capped at 24px with
4px rounded ends, gridlines are solid hairlines one step off the surface.

**The two series colours are validated for colour-blind separation** against
both the light and dark surfaces (worst-case ΔE 24.7 light / 26.8 dark against
a working threshold of 8). Blue is always money paid in; orange is always
interest — the same meaning on every chart. Please don't swap them casually.

**Nothing relies on colour alone.** Every chart has a legend, and every chart
has a "Show data table" toggle underneath it giving the same values as text.

**Light and dark themes** are both hand-picked rather than one being an
inversion of the other. The toggle is in the header.

**Responsive** from 360px upward. Charts measure their container and redraw at
real pixel size, so strokes and labels stay crisp instead of being scaled.

## Why the simulation labelling is built in

The brief specified that this "should not be designed in a way that could be
mistaken for a genuine bank statement or used as proof of funds." That
requirement is met structurally rather than by a footnote:

- a **Simulation** chip in the header, on every screen,
- a disclaimer in the footer of every page,
- a faint diagonal watermark behind the balance and the ledger,
- `noindex` metadata, so it cannot surface in search results without context,
- a print stylesheet that makes the disclaimer the most prominent element on
  the page, so it survives being printed or saved to PDF,
- no "download statement" or "export PDF" feature.

This set was deliberately pared back from something louder — the original
banner, badges and heavier watermark made the app read as a classroom exercise
rather than a finished product. What remains is quiet enough to look
professional and sufficient to keep the page honest about what it is.

**These are load-bearing, not decoration.** A version of this page with no
indication that the figures are modelled is a working proof-of-funds document,
which is a different artefact with different consequences for whoever builds
and supplies it. Please leave them in.
